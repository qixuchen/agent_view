Motivation: Change the Data, Not the Context

Proposal · 1 / 6
Data agents often fail not because they cannot write SQL, but because they misunderstand the data.

Existing: learn knowledge from failuresTK-Boost, MIRA

  • They mine misconceptions from failed tasks and store them as knowledge in text.
  • For every new task, the right piece must be retrieved and applied again.
  • The stored dataset stays unchanged; the fix is injected into the agent's context.

New: generate data artifacts

  • We turn knowledge into a data artifact: a derived view over the original tables.
  • No retrieval needed. The agent's context stays unchanged; what changes is the data it can query.
  • Agents benefit from these views that make the complex task/query simpler.

CREATE VIEW company_dim AS
SELECT p.bmCode, t.name_en, p.bmCompanyName AS name_zh,
       p.exchange, p.plate AS listing_board
FROM company_profile p
JOIN translation t ON t.name_zh = p.bmCompanyName;

Research Questions: Merge and Select

Proposal · 5 / 6
STAGE 2 & 3

Propose & Merge: which artifacts to propose and combine?

  • For each task, need to find the correct view that effciently fix the task / save the reasoning steps.
  • Views are proposed from many tasks, so candidates overlap.
  • Views can be joined, which increases coverage but hurts specificity.
  • Existing work: physical design tuners such as AutoAdmin that merge candidate views and indexes to fit a storage budget.
Related: AutoAdmin view merging (VLDB 2000); index merging (ICDE 1999); relaxation-based tuning (SIGMOD 2005)
STAGE 4

Select: which artifacts to materialize?

  • Utility of an artifact: a score related to # failures it fixes, the # of steps it saves, minus correct answers it breaks.
Selection constraints
  • Storage: total size of the materialized views.
  • # Tokens: the number of tokens required for agent to read an artifact.
  • Count: too many artifacts can mislead the agent.
  • Solution: Consider greedy / ILP.
Related: view selection (HRU 1996; Gupta, ICDT 1997)
